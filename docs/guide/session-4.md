# 4회차 보충 문서: 내 NestJS 서버

> 이 문서는 4회차 프롬프트가 만드는 내용의 자세한 약속입니다. 앞 회차 문서에 이어지며, 앞 문서와 다르면 이 문서를 따릅니다.

## 이 문서를 읽는 법

- 백틱 안의 글은 이름이나 값입니다. 글자 그대로 씁니다.
- 큰따옴표 안의 글은 화면에 나오는 글자이거나 코드에 들어가는 값입니다. 한 글자도 바꾸지 않습니다. 단, 프롬프트 마지막 참고 줄의 큰따옴표 안은 이 문서의 절 제목입니다.
- "쓰는 단계"는 그 내용을 만드는 프롬프트 번호입니다. 프롬프트 맨 앞의 `[2-14]` 같은 표시가 이번 단계입니다. 그 번호가 "쓰는 단계"나 줄 앞에 적힌 내용만 만들고, 다른 번호의 내용은 그 프롬프트를 받기 전에 만들지 않습니다.
- "만들지 않는 것" 절에 적힌 기능은 완료 브랜치 코드에 있어도 만들지 않습니다.
- 창고 쪽 이름은 공장 쪽 이름의 `factory`를 `warehouse`로 바꾼 같은 이름입니다.

## 이 회차에서 만드는 것

- 시작 상태: 화면이 강사 API 값으로 10초마다 바뀌고 실패 안내·과거 시각·조회 기록이 동작합니다. `backend` 폴더는 아직 없습니다.
- 끝 상태: `backend` 폴더의 NestJS 서버가 `http://127.0.0.1:3000`에서 켜지고, 처음 켤 때 오늘 기록(생산 100개, 출고 75개)을 만들어 `backend/var/state.json`에 저장합니다. 화면은 1단계와 같은 모습으로 이 서버의 값을 보여 줍니다.
- 이번에 건드리지 않는 곳: 화면 코드입니다. `public` 폴더에서는 마지막에 `public/config.js`의 `apiBaseUrl` 한 값만 바꿉니다.

프롬프트가 만드는 순서입니다. 이번 프롬프트 번호가 쓰는 단계에 있는 내용만 만듭니다. 아직 번호가 오지 않은 주소와 값은 미리 만들지 않습니다.

## 내 서버의 구성

쓰는 단계: 4-2, 4-4, 4-11

여기부터 대시보드 폴더 안 `backend` 폴더에 내 서버를 만듭니다. 4-2는 패키지 목록과 설정 파일까지이고 설치는 4-3에서 합니다. 시작 파일과 앱 모듈은 4-4에서 함께 만듭니다. 연결 주소를 바꾸는 일은 4-11에서 합니다.

### 약속: 4-2에 만드는 파일

내 서버는 `backend` 폴더의 NestJS(TypeScript)입니다. `nest new`나 `npm init`을 쓰지 않고 파일을 직접 만듭니다. 화면 코드는 고치지 않고, 마지막에 `public/config.js`의 `apiBaseUrl`만 "http://127.0.0.1:3000"으로 바꿉니다(`timeoutMs` `5000` 그대로).

`backend/package.json`의 값입니다.

| 키 | 값 |
|---|---|
| name | "aiops-dashboard-student-api" |
| version | "1.0.0" |
| private | true |
| description | "학생용 텀블러 생산·출고 교육 API" |
| engines | node ">=22" |
| scripts | build "tsc -p tsconfig.json", start "node dist/main.js", start:local "node --env-file=.env dist/main.js" |

패키지는 이것만, 버전 앞에 `^`·`~` 없이 씁니다.

| 구분 | 패키지와 버전 |
|---|---|
| dependencies | `@nestjs/common` 11.2.7, `@nestjs/core` 11.2.7, `@nestjs/platform-express` 11.2.7, `reflect-metadata` 0.2.2, `rxjs` 7.8.2 |
| devDependencies | `@types/node` 24.4.0, `typescript` 5.9.3 |

`backend/tsconfig.json`의 값입니다.

| 옵션 | 값 |
|---|---|
| target | ES2022 |
| module | CommonJS |
| moduleResolution | Node |
| lib | ["ES2022", "DOM"] |
| outDir | dist |
| rootDir | src |
| include | ["src/**/*.ts"] |

`backend/.gitignore`는 `node_modules/`, `dist/`, `var/`, `.env` 네 줄입니다.

### 약속: 4-4에 만드는 시작 파일

`src/main.ts` 첫 줄은 `import "reflect-metadata";`입니다.

| 항목 | 값 |
|---|---|
| CORS | origin "*", methods ["GET"], credentials false |
| 포트 | PORT, 없으면 3000(1~65535 정수가 아니면 "PORT 값이 잘못되었습니다." 오류) |
| 주소 | HOST, 없으면 127.0.0.1 |

- 전역 주소 접두어·검증 파이프·예외 필터·환경 설정 패키지는 넣지 않습니다.
- listen 뒤에 주소 줄을 따로 찍지 않습니다. 서버 창의 마지막 줄은 Nest가 찍는 `Nest application successfully started`입니다.

## 내 서버 설치·빌드·켜기

쓰는 단계: 4-3, 4-5 ~ 4-10, 4-12

내 서버의 설치와 빌드는 AI 도구가 자기 터미널에서 합니다. 켜기는 1회차 문서 '화면 서버 켜기' 절과 같은 순서로, 새 PowerShell 창을 열어 그 창에서 합니다. 이 새 창이 내 서버의 서버 창입니다. 사용자는 이 창에서 `[Nest]` 줄과 빨간 오류 줄을 봅니다.

### 약속

**4-3 설치.** `backend` 폴더에서 `npm.cmd install`과 `npm.cmd ls --depth=0`을 차례로 실행하고, `npm.cmd ls --depth=0`의 결과 줄을 답에 그대로 보여 줍니다. 취약점 안내가 나와도 `npm audit fix`는 실행하지 않고, 패키지를 더하거나 버전을 바꾸지 않습니다. 서버는 켜지 않습니다.

**4-5 빌드와 처음 켜기.** `backend` 폴더에서 `npm.cmd run build`를 실행합니다. 빌드 오류가 나면 서버를 켜지 않고 오류 줄을 알려 줍니다. 빌드가 끝나면 1회차 문서 '화면 서버 켜기'의 "켜기 전 확인"을 포트 3000으로 하고, 아래 명령으로 새 창에서 켭니다.

```powershell
Start-Process powershell -ArgumentList '-NoExit','-Command','cd C:\ai-class\tumble-dashboard\backend; npm.cmd start'
```

- 3000번 포트를 듣는 프로세스의 명령 줄에 `dist/main.js`가 있으면 내 서버가 이미 켜져 있는 것입니다. 새로 켜지 않고 "이미 켜져 있습니다"라고 알립니다. `dist/main.js`가 없으면 다른 프로그램이 3000번 포트를 쓰고 있는 것이니 끄지 않고 사용자에게 알립니다.
- 몇 초 뒤 3000번 포트를 듣는 프로세스가 생겼는지 봅니다. 생겼으면 새 PowerShell 창에서 내 서버를 켰다고 알립니다. 생기지 않았으면 다시 켜 보지 않고, 새 창의 빨간 줄을 복사해 붙여 넣어 달라고 사용자에게 말합니다. 사용자가 그 줄을 붙여 넣고 고쳐 달라고 하면 고친 뒤 같은 순서로 다시 켭니다.

**4-6 ~ 4-10 다시 빌드해 켜기.** `backend` 코드를 고친 번호는 마치기 전에 `npm.cmd run build`를 실행하고, 빌드가 끝나면 3000번 포트를 듣는 내 서버(명령 줄에 `dist/main.js`가 있는 프로세스)만 끈 뒤 위의 명령으로 새 창에서 다시 켭니다. 끄는 방법은 1회차 문서 '화면 서버 켜기'의 "다시 켤 때"와 같고 포트만 3000입니다. 내 서버가 꺼져 있었으면 끄지 않고 켜기만 합니다. 다시 켠 뒤 서버가 꺼진 예전 서버 창은 닫아도 된다고 사용자에게 알립니다. 사용자가 "내 서버를 다시 켜 주세요."라고 보내면 빌드 없이 끄고 다시 켜기만 합니다.

**화면 서버.** 화면 서버(4173)는 1회차 문서 '화면 서버 켜기' 절대로 켭니다. 내 서버를 다시 켜도 화면 서버는 그대로 둡니다.

## 기록과 시드 기록

쓰는 단계: 4-6

서버를 처음 켤 때 오늘 0시부터 켠 시각까지의 기록을 만들어 둡니다. 이 기록을 시드 기록이라고 부릅니다. 기록 한 건의 약속은 4-6에서 모양을 만들 때 씁니다.

### 약속: 기록 한 건

- 기록 한 건은 `id`(영문·숫자·`_`·`-` 1~100자), `kind`("production"·"shipment"), `quantity`(1 이상 정수), `occurredAt`, `receivedAt`, `processedAt`(없으면 null) 순서의 키입니다.
- 시각은 `Z`로 끝나는 ISO 글자이고 발생 ≤ 접수 ≤ 처리, 처리가 있으면 접수도 있습니다.
- 시각을 받아 한국 시간 날짜("2026-11-09" 꼴)로 바꾸는 도구도 함께 둡니다.
- 시드 기록이 이 모양을 지키게 만듭니다. 켤 때 읽은 상태 파일을 이 규칙으로 검사하지는 않습니다('만들지 않는 것' 절).

### 약속: 시드 기록

시드 기록은 상태 파일을 만들 때 만듭니다.

- 오늘 한국 0시부터 지금보다 2분 이른 시각까지를 같은 간격 점으로 나눕니다. 점 개수 = 올림(구간 ÷ 20분) + 1이고, 첫 점은 0시, 마지막 점은 구간 끝입니다.
- 생산을 모두 만든 뒤 출고를 잇습니다.
- 수량은 합계를 점 개수로 나눈 몫이고 나머지는 앞 기록부터 1씩 더합니다.
- 어느 시각도 지금보다 늦지 않습니다.

| 항목 | 생산 | 출고 |
|---|---|---|
| 수량 합계 | 100 | 75 |
| id | "seed-production-0"… | "seed-shipment-0"… |
| 발생 | 점 그대로 | 점보다 1초 뒤 |
| 접수 | 발생 2초 뒤 | 발생 2초 뒤 |
| 처리 | 접수 3초 뒤 | 접수 3초 뒤 |

## 기준 시각과 기록 목록

쓰는 단계: 4-7

기록 화면(`#/records/factory`, `#/records/warehouse`)이 읽는 기록 목록을 만듭니다. 아래는 기준 시각, 기록 목록의 검사, 기록 목록의 결과로 나눠 적었습니다.

### 약속: 기준 시각

기준 시각 `at`(없으면 지금)은 아래를 모두 지켜야 합니다.

- "2026-11-09T"처럼 날짜와 `T`로 시작하고 끝이 `Z`나 `+09:00` 꼴입니다.
- 시각으로 읽힙니다.
- 지금 이전입니다.
- 한국 날짜가 오늘입니다.

아니면 400 "오늘의 현재 이전 시각을 선택해 주세요."입니다. `at=`처럼 값이 빈 `at`은 없는 것이 아니라 이 400입니다. 통과하면 `Z`로 끝나는 ISO로 바꿔 씁니다.

### 약속: 기록 목록의 검사

- `records`는 `kind`가 `production`·`shipment`가 아니면 시각을 보기 전에 400 "생산 또는 출고 기록을 선택해 주세요."입니다.
- `from`은 없으면 기준 날짜 한국 0시이고, `to`는 없으면 기준 시각입니다. `from=`·`to=`처럼 값이 비어도 없는 것으로 봅니다.
- `from`·`to`는 `Z`나 `+09:00` 꼴이고 기준 날짜와 같은 한국 날짜이며 `from` ≤ `to` ≤ 기준 시각이어야 하고, 아니면 400 "조회 시간 구간을 확인해 주세요."입니다.

### 약속: 기록 목록의 결과

결과는 { `sessionId`, `viewTime`(기준 시각), `records` }입니다.

- 그 `kind`이고 발생 시각이 `from`~`to`(양 끝 포함)인 기록을 발생 시각 순으로 담습니다.
- 기준 시각보다 늦은 접수·처리 시각은 null로 바꾸고 `status`를 더합니다. 처리가 있으면 `completed`, 접수만 있으면 `processing-wait`, 둘 다 없으면 `receipt-wait`입니다.
- 시각은 글자가 아니라 숫자로 바꿔 비교합니다.
- 저장된 기록 자체는 바꾸지 않습니다.
- 기준 시각 검사와 기록 고르기, 기준 시각 뒤의 시각 가리기는 오늘 운영 자료에서도 다시 쓰도록 따로 둡니다.

## 오늘 운영 자료

쓰는 단계: 4-8, 4-9

오늘 운영 화면(`#/today`)이 10초마다 읽는 자료는 두 번에 나눠 만듭니다. 4-8에서 모양과 주소를 만들고 기준 시각 검사는 기록 목록과 같은 것을 씁니다. 4-9에서 두 현장의 값을 채웁니다.

### 약속: 4-8에 만드는 모양

`snapshot`의 키입니다.

- `schemaVersion` 1, `scenarioId`, `revision`, `changedAt`(상태 파일 값, 단 기준 시각보다 늦으면 기준 시각), `serverTime`(지금), `trainingOnly` true, `sites`, `services`, `incidents`
- `incidents` 뒤에 `viewTime`(기준 시각), `mode`(`at`이 없으면 "current", 있으면 "past"), `sessionId`를 붙입니다.

두 현장의 이름과 목표입니다. 4-8에서는 두 현장에 이름과 목표만 넣고 수량과 시각은 비워 둡니다(`null`). 4-9에서 채웁니다.

| 현장 | label | target | 쓰는 기록 |
|---|---|---|---|
| `sites.factory` | "텀블공장" | 120 | 생산 기록 |
| `sites.warehouse` | "물류창고" | 100 | 출고 기록 |

`services`의 값입니다.

| 서비스 | status | 나머지 |
|---|---|---|
| api | "normal" | note: "조회 서비스가 정상입니다." |
| alerts | "sent" | lastAttemptAt: 그 snapshot의 `changedAt`보다 1분 이른 시각, note: "모의 전송 성공 기록입니다. 실제 알림을 보내지 않았습니다." |

### 약속: 4-9에 채우는 현장 값

이 서버는 켠 뒤로 기록이 늘지 않습니다. 마지막 시드 기록이 처음 켠 시각의 2분 전이므로, 처음 켠 지 28분이 지나면 "기록이 30분 넘게 들어오지 않았습니다." 경고가 나오는 것이 맞습니다.

수량과 시각입니다.

- `completed`는 발생 시각의 한국 날짜가 기준 날짜와 같고 처리 시각이 기준 시각 이전인 기록의 수량 합이며, 합이 0이면 null입니다.
- `lastEventAt`·`receivedAt`·`processedAt`은 0시~기준 시각 기록 목록(`records`와 같은 계산)의 마지막 기록 값(없으면 null)입니다.
- `processingState`는 그 마지막 기록에 처리 시각이 있으면 "completed", 아니면 "waiting"입니다.

그래프와 사진입니다.

- `history`는 같은 목록(0시~기준 시각 기록 목록)에서 처리 시각이 있는 기록을 발생 시각의 UTC 정시(ISO)별로 더한 { `timestamp`, `quantity` } 배열(시각 순)입니다.
- `image`는 { url: (PUBLIC_BASE_URL 끝 / 뗀 값, 없으면 "http://127.0.0.1:" + (PORT 또는 3000)) + "/api/v1/images/factory"(창고 warehouse), alt: "생산 라인 참고 사진"(창고 "물류창고 참고 사진") }입니다.

현장 상태입니다. `status`는 아래 가운데 하나라도 맞으면 "warning", 아니면 "normal"입니다.

- 마지막 기록이 없습니다.
- 기준 시각이 마지막 발생보다 30분 넘게 늦습니다.
- `processingState`가 `completed`가 아닙니다.

`note`는 normal이면 "기록이 반영되고 있습니다."입니다. warning이면 아래 순서로 먼저 맞는 것 하나입니다.

| 순서 | 조건 | note |
|---|---|---|
| 1 | 마지막 기록이 없으면 | label + "의 기록이 없습니다." |
| 2 | 마지막 기록에 처리 시각이 없으면 | label + " 기록 처리를 기다리고 있습니다." |
| 3 | 30분 넘게 늦으면 | label + " 기록이 30분 넘게 들어오지 않았습니다." |

warning 현장마다 `incidents`에 아래 값으로 된 항목을 넣습니다.

| 키 | 공장 | 창고 |
|---|---|---|
| id | "FACTORY-FEED" | "WAREHOUSE-FEED" |
| scope | "factory" | "warehouse" |
| level | "warning" | 공장과 같음 |
| title | 그 note | 그 note |
| owner | "공장 데이터 담당자" | "창고 데이터 담당자" |
| action | "기록 수집과 처리 상태를 확인해 주세요." | 공장과 같음 |

## 기록을 다시 만들 때

쓰는 단계: 4-12

수업을 시작할 때(날짜가 바뀌면 "…의 기록이 없습니다." 경고가 나옵니다), 처음 켠 지 28분이 지났을 때 씁니다.

### 약속

이 서버에는 기록을 더하는 기능이 없습니다. 기록을 지금 기준으로 다시 만들 때는 AI 도구가 아래 순서로 합니다. 코드는 바꾸지 않으므로 빌드하지 않습니다.

1. 절 '내 서버 설치·빌드·켜기'대로 3000번 포트를 듣는 내 서버를 끕니다. 꺼져 있으면 이 순서를 건너뜁니다.
2. `backend/var/state.json`을 지웁니다. `backend/var` 폴더와 다른 파일은 그대로 둡니다.
3. 같은 절의 명령으로 새 창에서 내 서버를 다시 켭니다. 켤 때 시드 기록이 지금 시각 기준으로 새로 만들어집니다.
4. 화면 서버(4173)가 꺼져 있으면 1회차 문서 '화면 서버 켜기' 절대로 함께 켭니다.
